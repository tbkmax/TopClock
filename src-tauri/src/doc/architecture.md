# Rust application architecture

The `open_settings_folder` command uses the managed settings path, ensures its parent exists, and launches that directory in Windows Explorer. It does not accept a caller-supplied path.

`display_identity.rs` queries active Windows display targets and maps their device paths to Tauri's GDI display names. `main.rs` reconciles one transparent clock window per enabled desktop display every two seconds, creating and removing secondary windows as displays change. Target paths identify saved display preferences; a monitor moved to another connector can receive a different path. When Windows supplies no target path, a GDI display slot is the fallback and may change after reordering. Each display preference stores an independent visible flag and position relative to that display's origin, without restricting that position to the display. Missing preferences default to visible, including newly connected displays. The legacy absolute `position` is migrated to the matching display on first startup. `ClockSettings` and `TimerSession` remain shared across all clocks; each window has its own menu flag, click-through and proximity state.

[main.rs](../main.rs) owns the native runtime. [settings.rs](../settings.rs) owns the durable settings schema, defaults and validation. [addons.rs](../addons.rs) validates built-in add-on instances and owns Timer session calculations. [hotkeys.rs](../hotkeys.rs) registers enabled action shortcuts with Windows. [fonts.rs](../fonts.rs) enumerates Windows-installed fonts. The parent [Tauri architecture](../../doc/architecture.md) describes package configuration.

| Unit | Responsibility |
| --- | --- |
| `ClockState` | In-process config mutex, per-window menu flags, active display windows, settings path and hotkey errors |
| `PersistedConfig` | Shared clock settings and Timer session, per-display preferences and legacy position, defined in `settings.rs` |
| `AddonInstance` | ID, type, enable state, above/below placement, size percentage and validated type options |
| `TimerSession` | Durable running flag, accumulated elapsed time, start epoch and finished state |
| `get_font_families` | Read and deduplicate font families from the Windows GDI font table |
| Tauri commands | Shared settings and Timer actions, per-display visibility and bounds, startup registry switch, menu state, window controls, folder and release page opening, and quit |
| `start_monitor` | Poll configured modifier key (Ctrl, Alt, or Shift), cursor proximity and window position; set click-through and emit events |
| `start_hotkeys` | Register enabled system-wide action shortcuts, dispatch their native actions, and report unavailable combinations |
| `set_click_through` | Toggle Win32 `WS_EX_TRANSPARENT` while preserving `WS_EX_LAYERED`, then refresh the window frame so the input style takes effect without the earlier GDI white flash |
| Tray setup | Open settings and quit actions |

At startup, Rust loads `settings.json` from Tauri's app config directory (`%APPDATA%\topclock\settings.json`), migrating from legacy `com.maxtc.topclock` if present. It defaults missing fields, salvages unrelated clock settings if add-on data cannot deserialize, and clears semantically invalid add-on instances without resetting valid clock appearance. The old `timer_addon_enabled` flag becomes a Countdown add-on once. An older default `Ctrl+Q` Quit binding becomes `Ctrl+Alt+Q`; action shortcuts get off-by-default enable flags. Rust writes the config, builds the configured `main` and `settings` webviews, then reconciles enabled display clocks. A display with no saved position starts near its top-right corner.

The current settings schema includes clock appearance, time layout, animation choices, update preference, `shortcuts`, `addons`, and a saved warning dismissal for Timer mode changes. `addons` is an ordered list; Date and Timer allow one instance each, Region clock allows up to 12, and the overall limit is 16. [addons.rs](../addons.rs) validates IDs, type-specific options, placement and relative text size from 10% through 100%. Date accepts an optional boolean `show_weekday`; Region clock accepts an optional boolean `show_label`. Omitting these fields remains valid for saved instances created before the switches existed. The legacy Timer migration creates an instance at 30%; existing saved sizes are preserved. Adding a similar built-in type requires one validation branch and a frontend catalog/formatter entry; saved data cannot execute code. `update_settings` rejects invalid changes, rolls back memory on write failure, and emits `clock-settings-changed`. A running Timer cannot change its mode or duration. Its `TimerSession` is separate from appearance settings, persists on Start/Pause/Reset, and uses the stored wall-clock start time to resume after restart. The monitor marks a Countdown finished at zero and emits `timer-state-changed`.

The configured modifier key is polled by `start_monitor` for each clock window and stays active for dragging and its menu. Setup enables click-through before showing a clock; the monitor reconciles the visible window on its first poll. Later polls toggle `WS_EX_TRANSPARENT` only when needed, retain `WS_EX_LAYERED`, send `ctrl-state` and `proximity` to that clock, and save its display-relative position after movement settles. Saved positions restore without edge clamping. [hotkeys.rs](../hotkeys.rs) registers enabled action bindings once for the application. The Windows Run registry key stores sign-in launch separately.

The command and event boundary is used by [frontend code](../../../src/doc/architecture.md). [default.json](../../capabilities/default.json) lists frontend permissions. Unit tests cover settings validation, add-on validation, Timer resume/completion, hotkey parsing and font enumeration. The font list is read on request, while only the selected family name is persisted. These built-in add-ons do not load third-party code or network data.
